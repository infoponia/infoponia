## D-95 — La verificación la hace Claude Code: se retiran la verificación a mano y los datos de prueba

- Fecha: 23/11/2026
- Estado: **vigente** (pedida por el estudiante el 23/11/2026).
- Decidió: el estudiante, durante CMP-01; redacción de Claude Code.
- Antes:
  - Cada tarea traía una «Verificación a mano» (pasos para el estudiante) y Claude Code dejaba la base local cargada con un comando propio (`cargar_datos_de_verificacion`, D-56 y los
    `<app>/verificacion.py`). Las revisiones pendientes se anotaban en `docs/revisiones_pendientes.md` y se tachaban a mano (regla M5).
  - El estudiante tiene una entrega próxima y necesita dedicar su tiempo a implementar: verificar a mano le roba demasiado. Lo que una tarea posterior detecta y corrige sin costo no justifica una revisión manual.
- Decisión:
  1. **La verificación la hace Claude Code antes de cerrar cada tarea** (`docs/patrones/verificacion_por_claude.md`): (a) un **recorrido** de punta a punta con el cliente de Django, por rol y estado
     (`<app>/tests/test_recorrido_<tema>.py`); (b) si la tarea tiene pantallas, una **verificación visual con un navegador real** (Playwright + Chromium; `<app>/tests/test_visual_<tema>.py`), mirando las capturas;
     (c) si tiene migración, `sqlmigrate` de la nueva y aplicarla en la base de pruebas. El resultado va al «Cierre» en tres listas: **Verifiqué**, **Lo cubre una prueba** y **No pude verificar**.
  2. **Pasos para replicar.** Al final de cada ronda (cuando Claude Code da el mensaje de commit y la propuesta de M3), le entrega al estudiante, **aunque no tenga tiempo de hacerlos**, los pasos de verificación
     a mano **con mucho detalle**, para que pueda replicarlos si se hace tiempo: precondiciones, qué crear a mano (ya no hay datos cargados), dónde tocar, qué escribir y qué tiene que ver, por rol y por estado.
     Quedan en el «Cierre» de la tarea y en el texto del PR. Son **opcionales**: no hay revisiones a mano pendientes ni se tachan.
  3. **Se retira el esquema anterior:** el comando `cargar_datos_de_verificacion`, `core/verificacion.py`, los `<app>/verificacion.py` de `maestros`, `iot`, `produccion` y `comercial` y sus pruebas, y
     `docs/patrones/datos_de_verificacion.md`. La regla M5 y `docs/revisiones_pendientes.md` quedan **congelados** (historial). Las tareas que todavía nombran el cargador o traen «Verificación a mano» no se
     reescriben: manda `CLAUDE.md` (se ignora el cargador y cada paso a mano se convierte en un recorrido).
  4. **Dependencia nueva, solo de desarrollo:** Playwright (`requirements-dev.txt`, que incluye `requirements.txt`). No va en `requirements.txt`, que instalan el CI y Render. Las pruebas visuales se corren aparte
     (`INFOPONIA_VISUAL=1` y `--tag visual`) y usan su propia base de pruebas; las corre Claude Code, y el estudiante no necesita instalar nada.
- Por qué: casi todo lo que se verificaba a mano lo puede hacer una prueba (el flujo, los roles, los estados) y, para lo visual, un navegador automatizado; lo que una tarea posterior corrige sin costo no justifica la revisión manual.
  Lo que **no** se corrige después (una migración ya aplicada en Neon, datos de producción, el despliegue) se sigue cuidando y, cuando no se puede automatizar, figura en «No pude verificar».
- Fuentes: pedido del estudiante (23/11/2026); `CLAUDE.md` (M1 a M5); D-56; `docs/patrones/datos_de_verificacion.md` (retirado).
- Consecuencias:
  - Cambian `CLAUDE.md` (la regla «Verificación (la hace Claude)», M2, M3, M4 y M5), `docs/README.md` («Ciclo de una tarea»), `docs/tareas/_plantilla.md`, `.claude/rules/pruebas.md` y
    `docs/patrones/verificacion_por_claude.md` (nuevo).
  - Se borra código ya mergeado (cargadores y sus pruebas), por pedido explícito del estudiante.
  - El estudiante sigue mirando antes de mergear: que el CI esté en verde y la lista «No pude verificar».
