## D-44 — Documentación completa por ronda y tareas por bloque funcional

- Fecha: 19/11/2026
- Decidió: el equipo (validada por el estudiante el 19/11/2026) (propuesta de Claude, a pedido del estudiante que escribe la documentación)
- Antes: el esquema de documentación (18/11/2026) armaba el contexto «justo a tiempo»: el extracto del caso de uso, el
  del modelo y los patrones se escribían al redactar cada tarea. Las tareas salían una por servicio o por mitad de un
  caso de uso (MAE-01, MAE-01b, MAE-02a y MAE-02b). Resultado: la persona que programa depende de que la documentación de
  la próxima tarea esté lista, y cada tarea chica paga de nuevo el costo de arrancar (plan, aprobación, lectura, cierre).
- Decisión:
  - **Una ronda es un conjunto de pantallas del prototipo** que el equipo decide construir junto (la primera: datos
    maestros y producción, `docs/tareas/ronda_produccion_1.md`). Antes de programar la primera tarea de una ronda, el repo
    tiene **toda** la documentación que la ronda necesita: el plan completo de tareas, un extracto por cada caso de uso, el
    extracto del modelo de todas las clases, los patrones que se usan por primera vez, los datos de migración y los
    disparadores. Programar una tarea no obliga a escribir documentación nueva: solo a completar su «Cierre».
  - La documentación se entrega por lotes (cada lote es completo: ningún lote deja una tarea a medias), pero el **plan
    de tareas es siempre completo** desde el primer lote.
  - **Una tarea es un bloque funcional**: los casos de uso que comparten modelo, servicios y pantallas (por ejemplo, todo
    el ABM de sectores y cultivos). Se implementa en una sola sesión de Claude Code y un solo PR. Tiene «Pasos» ordenados
    con pruebas por paso; el plan se aprueba una sola vez (`CLAUDE.md`). Tamaño de referencia: 4 a 10 casos de uso o un
    caso de uso grande con sus pantallas. Una tarea no se parte salvo que su archivo lo diga.
  - **Regla de faltante (L9 de `CLAUDE.md`):** si a una tarea le falta un dato, Claude Code frena y lo informa; la
    persona lo corrige en la documentación y no se inventa en el código.
- Por qué:
  - El costo de una tarea se paga en leer, planificar y cerrar; con tareas más gruesas ese costo se reparte entre más
    casos de uso y se programa más rápido.
  - Una tarea gruesa solo es segura si Claude Code tiene todo lo necesario sin buscar: por eso la documentación completa
    es condición de las tareas gruesas, no un lujo.
  - Escribir los extractos de toda la ronda de una vez permite detectar contradicciones entre casos de uso (por ejemplo,
    dos casos que reservan el mismo insumo) antes de que estén en el código.
- Fuentes: `CLAUDE.md` (principio «Enrutar, no cargar»); esquema de documentación de 18/11/2026; MAE-01 a MAE-02b.
- Consecuencias:
  - Cambian las descripciones de `docs/README.md`, `docs/modelo/README.md`, `docs/tareas/README.md`,
    `docs/tareas/_plantilla.md`, `docs/temas_abiertos.md` y `CLAUDE.md` (agregados L9 y el plan único).
  - «Enrutar, no cargar» se mantiene: más documentación en el repo no significa más lectura por tarea; la tarea nombra
    solo lo que necesita.
  - Las tareas chicas ya hechas (MAE-01 a MAE-02a) no se tocan.
  - El riesgo es que una tarea gruesa salga con errores que se detectan tarde: la mitigación son las pruebas por paso y
    el cierre con verificación a mano. Si una tarea resulta demasiado grande, se parte en una decisión nueva.
- Estado: vigente
