## D-101 — Las bases de prueba no piden permiso; la de desarrollo, sí

- Fecha: 24/11/2026
- Decidió: el estudiante, al pedir que recrear la base de pruebas no requiera aprobación
- Antes: `CLAUDE.md` pedía frenar y preguntar antes de borrar datos, también «los datos de prueba», y contaba como borrar «descartar la base de `--keepdb`». Esa regla nació porque una vez se borraron 19 tablas de la base local para arreglar una migración. Con ella, algo inofensivo como recrear `test_infoponia` (o los clones de `--parallel`) obligaba a aprobar.
- Decisión:
  1. **Las bases de prueba** (las que Django crea con nombre `test_…`, y sus clones, en el servidor local): Claude Code hace lo que necesite sin preguntar (recrearlas, descartarlas, `--noinput` sin `--keepdb`, `flush` o `TRUNCATE` por las pruebas). `manage.py test` crea y descarta sus propias bases: no requiere permiso.
  2. **La base de desarrollo** (la de `runserver` en `localhost:5433`): sigue igual de fuerte: toda pérdida de datos se pregunta (`DROP`, `DELETE` o `TRUNCATE` a mano, `flush`, `migrate <app> zero`, `--fake` seguido de un borrado, borrar la base o su archivo). Si una migración no se puede deshacer, no se arregla tocando las tablas.
  3. **Producción** (Neon y Render) y cualquier base que no sea la local siguen prohibidas.
  4. **Cómo distinguirlas:** es de prueba solo si su nombre empieza con `test_` y está en el servidor local; si no, o si no se puede confirmar, o si `DATABASE_URL` apunta a otro servidor, es la de desarrollo. Un comando manual usa por defecto la de desarrollo: se pregunta, salvo que apunte explícitamente a una base `test_…`.
- Por qué: la regla protege datos que cuestan trabajo reponer; una base de prueba se recrea sola en cada corrida y no tiene nada que proteger. Distinguirlas por el nombre y el servidor no deja lugar a error.
