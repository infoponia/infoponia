## D-70 — Integración con el nodo central: API HTTPS propia, token, sin dependencias nuevas y Node-RED como nodo de referencia

- Fecha: 21/11/2026
- Decidió: el estudiante, en el análisis del módulo IoT (18 al 20/11/2026: D3, D5, R6 y «Node-RED en lugar del simulador» de
  `IoT_cambios_a_registrar.md`), que esta decisión pasa al repo en el lote IoT 0.
- Antes:
  - La nota de presentación prevé integrar con MQTT (broker Mosquitto). El hardware del cliente (Marinelli et al., CACIC 2020) usa
    Raspberry Pi con Mosquitto y Node-RED.
  - `CLAUDE.md` prohíbe agregar dependencias sin permiso, y lo habitual en Django para una API es Django REST Framework.
  - Se había planeado un simulador propio en Flask, en otro repositorio (P8), descartado el 19/11/2026.
- Decisión:
  1. **InfoPonia expone una API HTTPS propia para el nodo central**, dentro del mismo proyecto y del mismo servicio de Render, con la
     versión en la ruta: `/api/iot/v1/`. Las rutas, los mensajes, los códigos y los motivos de rechazo son el **contrato**
     (`docs/api/nodo/`, lote IoT 2). El contrato es de InfoPonia: si cambia, se cambia primero el documento y después el código.
  2. **Sin bibliotecas nuevas.** Vistas comunes de Django que reciben y devuelven JSON, exentas de la protección CSRF (que existe para los
     formularios del navegador) y sin sesión. Las protege el token. No se agrega Django REST Framework.
  3. **El token del nodo.** Se genera con `secrets.token_urlsafe(32)` y se guarda **solo su SHA-256** en `SistemaIoT.token_resumen`
     (64 caracteres, único), con las mismas funciones puras que el enlace del cliente (`core/enlaces.py`, `nuevo_token` y `resumen_de`,
     D-65). Si `core/enlaces.py` todavía no existe cuando se programa IOT-02, IOT-02 lo crea tal como lo describe
     `docs/patrones/enlace_del_cliente.md` y COM-04 lo reutiliza (y al revés). El nodo lo manda en cada pedido en el encabezado
     `Authorization: Bearer <token>`. Se busca el sistema por el resumen: no se comparan tokens. El token nunca va a la base, a la
     auditoría ni a los registros de errores.
  4. **La lógica no depende del transporte.** Cada vista traduce el mensaje y llama a un servicio del dominio (`iot/servicios/`), el
     mismo que probaría un mensaje que llegara por otra vía. Así, MQTT con un agente puente no cambia ninguna regla (IOT-ENT-INF,
     «Requisitos especiales»).
  5. **Límite de mensajes.** Cada nodo puede mandar hasta 120 pedidos por minuto y cada pedido pesa hasta 256 KB y trae hasta 500
     lecturas. Lo que excede se rechaza con HTTP 429 o 413 sin procesar nada. El contador vive en la caché de Django (sin dependencias:
     la caché local por proceso alcanza para un solo proceso de gunicorn). Los números son del contrato y se pueden ajustar ahí.
  6. **Node-RED es el nodo de referencia.** No se construye un simulador. El nodo de prueba es un flujo de Node-RED que corre en la
     computadora del estudiante, con equipos simulados y un panel para forzar condiciones; se exporta como JSON y se versiona en
     `docs/api/nodo/node-red/` (lotes IoT 2 y 3). Es el mismo adaptador que usaría el Jardín Botánico, cambiando los equipos simulados
     por nodos «mqtt in» de su Mosquitto. **Node-RED no es una dependencia del repo**: no se instala con `requirements.txt`.
- Por qué:
  - Una API propia y versionada es lo que permite que cualquier organización conecte su nodo sin tocar InfoPonia (adaptabilidad).
  - Django alcanza para recibir JSON; una dependencia nueva solo para eso no se justifica en un trabajo de este tamaño.
  - El token guardado como resumen cumple «sin credenciales en texto plano» (SEG-02) con la misma técnica que ya usa el repo.
  - Node-RED ahorra el desarrollo del simulador y es el software que ya usa el hardware del cliente.
- Fuentes: `IoT_cambios_a_registrar.md` (D3, D5, R6, «Node-RED en lugar del simulador», «Diferencias con la nota de presentación»);
  IOT-REG-SIS (reglas «Token» y «Guía de integración del nodo»); IOT-ENT-INF e IOT-RSV-CMD («Requisitos especiales»); D-65.
- Consecuencias:
  - IOT-02 genera y regenera el token (IOT-REG-SIS, IOT-MOD-SIS). IOT-03 crea la API de lecturas, estados, modo y anuncio, con su
    autenticación, y el patrón `docs/patrones/api_de_dispositivos.md` lo propone Claude Code al cerrarla. IOT-05 suma el retiro y el
    resultado de los comandos.
  - Las pruebas de la API usan los ejemplos JSON del contrato (`docs/api/nodo/ejemplos/`), sin Node-RED.
